### Phase 27 -- Model Context Protocol (MCP)

Development_plan's fifth "Future Phase": MCP Client, MCP Server,
External Tool Integration. One new crate, `mcp`.

- **Spec version, decided empirically, not assumed**: two MCP revisions exist as of this phase (August 2026). 2026-07-28 -- the actual current/latest, finalized three weeks before this phase was written -- replaces the stateful `initialize`/`initialized` handshake and session-ID model entirely with self-contained, stateless requests. It's real, but by its own release notes barely adopted (official SDK support still beta at release) and explicitly designed so new clients fall back to the 2025-11-25 handshake for "most of the deployed ecosystem for some time." Not left as an assumption either way: `@modelcontextprotocol/server-filesystem` `2026.7.10` -- a real, currently-published reference server, installed from the real npm registry -- was spawned and probed directly. Requesting `protocolVersion: "2025-11-25"` in a genuine `initialize` call got back exactly `"2025-11-25"`, with real `tools/list`/`tools/call` round trips against a real file confirming the wire shapes. That's the version this crate targets, the same reasoning already used for the Rust 1.75 toolchain wall and the `pdf-extract`/`image`/`uuid` pins: pick what's actually confirmed to work, document why, don't guess.
- `protocol.rs`: JSON-RPC 2.0 envelope plus MCP's lifecycle/tools types, field shapes taken directly from the real fetched schema (`modelcontextprotocol/modelcontextprotocol`, `schema/2025-11-25/schema.json`, GitHub raw content, not recalled from training). Two details the schema alone didn't make obvious, both confirmed by manually probing the real reference server: a *tool-level* failure arrives as an ordinary JSON-RPC result with `isError: true`, not a protocol-level `error` object -- only a genuinely unrecognized method produces one; and real servers attach extra fields (`execution`, `outputSchema`) this crate doesn't act on, handled by preserving rather than rejecting them (`ServerCapabilities::other` via `#[serde(flatten)]`).
- `transport.rs`: line-delimited JSON-RPC framing (one `\n`-terminated message per line, MCP's stdio transport), generic over any `BufRead`/`Write` pair -- the same `LineTransport` serves a spawned child's pipes (`client`), this process's own stdin/stdout (`server::serve_stdio`), and an in-memory buffer in tests. A bounded per-line size cap (16 MiB) exists specifically so a broken or hostile peer streaming data with no newline can't grow this process's memory without bound.
- `client::McpClient`: spawns a peer as a real subprocess, performs the real `initialize`/`notifications/initialized` handshake, `list_tools`/`call_tool`. Synchronous, matching `tool_framework::Tool::execute`'s own signature exactly, the same reasoning `network::HttpClient` (Phase 14) already used for the identical constraint. One `Mutex`-guarded connection per client, which also structurally enforces this phase's one deliberate concurrency scope limit: at most one request in flight at a time, matching how every real server tested against here is actually used.
- `server::serve`/`serve_stdio`: exposes this assistant's own `ToolRouter` as an MCP server. `tools/call` is routed through `ToolRouter::execute` -- the *exact same* validate/permission-check/timeout pipeline a locally-issued call goes through (TCLIS SS1: the LLM never touches the OS directly, only through this pipeline) -- so an external MCP client asking this assistant to run a tool is just another caller of that same pipeline, not a separate, less-guarded path. Bridges into the router's `async fn execute` from a synchronous read loop via a `tokio::runtime::Handle` passed in explicitly (not `Handle::current()`), which also makes it directly testable: a plain `#[test]` builds its own throwaway `Runtime`, hands `serve` its handle, and drives a full scripted exchange with no subprocess needed.
- `bridge.rs` -- **the "External Tool Integration" itself**: `to_input_schema`/`to_json_schema` convert between MCP's arbitrary JSON Schema and this workspace's closed `tool_framework::ParamKind`, in each direction honestly, not silently. `tool-framework::ParamKind` gains an `Any` variant (accepts any JSON value) for JSON Schema shapes the existing five variants can't represent -- nested objects, `enum`/`oneOf`/`anyOf`, typed arrays, a missing or multi-valued `"type"` -- precedented directly by Phase 8's own `StringArray` addition for the same kind of gap; every `ParamKind::` call site across the workspace is a constructor, not an exhaustive match, so the blast radius was confirmed to be zero before adding it. Every declared remote property becomes a `ParamSchema` entry (as `Any` when nothing more specific applies) specifically so `InputSchema::validate` doesn't reject a legitimate remote-tool argument as `UnexpectedParam`; a schema relying on `additionalProperties` instead of declaring its properties is a named, undefended limitation, not a hidden one. `McpToolProxy` registers every bridged tool at `PermissionLevel::Moderate` and `ToolCategory::Mcp` (new variant) *regardless* of the remote tool's own `annotations` -- the real fetched schema's own field-level comment says a client should never make a tool-use decision from an untrusted server's hints, confirmed directly rather than inferred, so this crate doesn't read them for trust at all. Proven concretely, not just declared: a stub tool that's `Administrator` locally is only `Moderate` once bridged (`permission_integration.rs`), and a `PermissionManager` configured to deny still blocks a bridged call end to end.
- **Deliberately not built this phase**, each with its own documented reasoning in `lib.rs`/`bridge.rs`: a model-callable "connect to a new MCP server" tool (`Tool::execute` has no path back to the live `ToolRegistry` it's dispatched from -- the same class of gap Phase 7 named rather than guessed around), Resources/Prompts/Sampling/Roots/Elicitation (no existing analog in this workspace's architecture to bridge into yet), Tasks (experimental in 2025-11-25, substantially reworked as an optional extension in 2026-07-28 -- the least stable part of either revision), Streamable HTTP transport (stdio covers every real use case and reference server tested against; `LineTransport`'s generic reader/writer means adding it later doesn't touch the framing layer).
- **Real, not simulated, subprocess-boundary testing, twice over**: `src/bin/mcp-stub-server.rs` is a genuine second binary (auto-built by Cargo, no non-Rust dependency) serving `tool-framework`'s existing stub tools over real stdio; `tests/client_server_roundtrip.rs` spawns it as an actual child process and drives `McpClient` against it over real OS pipes -- initialize, list, call, a genuinely-enforced timeout, and the full bridge-into-`ToolRegistry` path, all across a real process boundary, not an in-memory stand-in. Separately, `tests/real_reference_server_interop.rs` re-runs the actual manual probe against the real `@modelcontextprotocol/server-filesystem` package via `npx`, `#[ignore]`d so the default suite stays free of any npm/node dependency; run explicitly during this phase and confirmed passing for real, including that the real server's response really does carry `annotations` this crate then deliberately ignores.
- 617/617 tests passing (+48 over Phase 26), across 40 verified crates (+1: `mcp`). `cargo fmt --all -- --check` clean workspace-wide; `clippy --all-targets -D warnings` clean across all 40 verified crates; `cargo doc --no-deps` zero warnings, rechecked including `mcp`.

### Phase 26 -- RAG System

Development_plan's fourth "Future Phase": Document Indexing, PDF
Support, Knowledge Base, Local Search. One new crate, `rag` -- a
genuinely separate store from `memory::MemoryStore` (DBDMS's own data
model already distinguishes "Long-Term Memory" from "Semantic Memory:
embedded documents and notes" as different concerns), built on the same
proven persistence shape: SQLite for durability, an in-memory
`vector_db::VectorIndex` mirror for search.

- `chunking::chunk_text`: real, deterministic word-count sliding-window chunking with configurable overlap, deliberately not attempting sentence/paragraph-aware segmentation (that needs real language understanding to do honestly -- abbreviations, decimals, and quoted speech all break a naive `.`-based splitter). A hand-traced-then-python-script-double-checked test caught a wrong chunk-count assumption before it shipped (250 words at max_words=100/overlap=20 is 3 chunks, not 4 -- the third window's end clamps to the real text length one step earlier than a quick mental count suggests).
- `pdf::extract_pdf_text` wraps `pdf-extract`, pinned `=0.6.5` (0.7.x needs `edition2024`, confirmed empirically, the same wall class `vision`'s `image` pin and `memory`'s `rusqlite` pin already document). **A real gap found while building this module's own test fixture**: generating a test PDF via ImageMagick's `convert` produces a PDF with no extractable text layer at all -- it rasterizes the text into an embedded image, the same as scanning a printed page. Both `pdf-extract` and the system's own `pdftotext` correctly report empty output against it. The fixture is instead a minimal, hand-built, spec-correct PDF with a real text-showing content stream, independently verified with `qpdf --check` and `pdftotext` before being trusted as this crate's test input.
- `store::KnowledgeBase`: real SQLite schema (`documents`/`chunks`/`chunk_embeddings`) plus the same `RefCell<VectorIndex<Id>>`-mirror-rebuilt-on-open pattern `memory::MemoryStore` already proved out. `index_document` detects PDF vs. plain text by extension; an empty result (a PDF with no text layer) indexes successfully with zero chunks -- a real, honest outcome, not an error. `forget_document` deletes children before parents (`chunk_embeddings` -> `chunks` -> `documents`) and returns `false`, not an error, for an unknown id, matching `MemoryStore::forget`'s own precedent. Persistence across reopening the same SQLite file is tested for real, not assumed from the schema alone.
- Four new tools (`ToolCategory::Development`): `search_knowledge_base`/`list_indexed_documents` are `ReadOnly`; `index_document` is `Moderate` (creates new persistent data, the same reasoning `write_file`/`create_file` already get that level for); `forget_document` is `Destructive` (irreversible data loss, matching `delete_file`'s precedent -- a meaningfully higher stakes action than indexing, not the same level).
- `integration-tests/tests/cross_crate_flows.rs`: `ocr_extracted_text_flows_into_the_knowledge_base_and_is_found_by_search` -- a genuine cross-*phase* flow, not just cross-crate: `ocr` (Phase 23) extracts real text from a real image, `rag` (Phase 26) indexes and finds it. **A second real OCR-accuracy finding surfaced building this test**: a first-attempt 500x100 fixture had tesseract genuinely misread the leading "Pho" as "9" and clip the trailing "rgy" -- real imprecision at an image's edges, confirmed by hand and fixed with a wider, better-margined canvas rather than papering over it with a looser assertion.
- 569/569 tests passing (+27 over Phase 25), across 39 verified crates (+1). `cargo fmt --all -- --check` clean workspace-wide; `clippy --all-targets -D warnings` clean across all 39 verified crates; `cargo doc --no-deps` zero warnings, rechecked including `rag`.

### Phase 25 -- Multi-Agent System

Development_plan's third "Future Phase": Planner Agent, Research Agent,
Coding Agent, Memory Agent, Security Agent. One new crate, `agents`,
built around a real, new piece of architecture -- `AgentMessage`
dispatched by `Coordinator` -- with every concrete agent wrapping an
already-real crate rather than reimplementing its capability.

- `message::AgentMessage` and `coordinator::{Agent, Coordinator}`: the genuinely new part of this phase. `AgentMessage` (`sender`, `receiver`, `task_id`, `payload`, `timestamp`, `priority`) traces directly to Ai_reasoning SS13's own sentence describing agent communication. `Coordinator::dispatch` deliberately mirrors `tool_framework::ToolRouter::execute`'s exact pipeline one layer up -- lookup by name, `spawn_blocking` + enforced timeout, a structured `DispatchResult` that's never a bare Rust error -- reusing a pattern this workspace already validated rather than inventing a second one for the same underlying problem (route a named request, bound its time, report what happened).
- `planner_agent::PlannerAgent` wraps `planner::Planner` (Phase 6) unchanged.
- `memory_agent::MemoryAgent` wraps `memory::MemoryStore` (Phase 5) behind `Arc<Mutex<_>>`, matching `search::MemorySearchProvider`'s own established sharing pattern for this exact type.
- `research_agent::ResearchAgent` wraps `search::SearchEngine` (Phase 13) -- **local search only**, said explicitly in its own doc comment: PRD SS3's "no cloud dependency" non-goal means "research" here means this assistant's own files/memory/commands, never the web, and no web-search capability exists anywhere in this workspace to wrap even if it wanted to.
- `code_agent::CodeAgent` wraps `coding_agent`'s real analysis/diagnostics/template-generation functions (Phase 24) -- named `code_agent`, not `coding_agent`, specifically to avoid shadowing the `coding-agent` crate dependency's own name in scope. Freeform generation (needing a live `ResponseGenerator`) is deliberately left to `coding_agent::tools::GenerateCodeTool` rather than duplicated here -- that tool already has a clear place for managing one.
- `security_agent::SecurityAgent` wraps `tool_framework::ToolRegistry` lookups against real, already-assigned `PermissionLevel`s -- reports what a set of named tools is actually permissioned at (TCLIS SS6's real levels), not a heuristic or invented risk score. `requires_confirmation_count` counts tools above `Safe`, matching `permission-manager::SecurityRules`'s own default `auto_approve_at_or_below: Safe` exactly.
- **A real finding, corrected before it shipped as an overclaim**: `security_agent`'s first doc comment draft described a "natural pairing" with `PlannerAgent` (check the risk of a plan's tools). Checking `planner::Planner::create_plan`'s actual source showed every `PlanStep::tool` is hardcoded `None` -- picking a *specific* tool out of a broad `Intent` category genuinely needs language understanding a keyword classifier can't honestly provide, the same reason `planner`'s own doc comment defers multi-step decomposition to a working `llm-runtime`. The doc comment was rewritten to say so plainly (a pairing real "in principle," not yet in practice) rather than left overselling a connection that doesn't exist yet.
- `integration-tests/tests/cross_crate_flows.rs`: `research_memory_and_security_agents_cooperate_through_one_coordinator` -- three real agents (not two) cooperating through one shared `Coordinator` in a single find-then-remember-then-check-risk scenario, this workspace's first proof the multi-agent architecture actually orchestrates multiple agents together, not just that each works in isolation.
- 542/542 tests passing (+30 over Phase 24), across 38 verified crates (+1). `cargo fmt --all -- --check` clean workspace-wide; `clippy --all-targets -D warnings` clean across all 38 verified crates; `cargo doc --no-deps` zero warnings, rechecked including `agents`.

### Phase 24 -- Coding Agent

Development_plan's second "Future Phase": Code Generation, Project
Analysis, Debugging. One new crate, `coding-agent`, structured
differently from Phase 23 on purpose -- three internal modules rather
than three crates, since none of these three capabilities need a
distinct external dependency the way `screenshot`/`ocr`/`vision` each
did (ImageMagick, tesseract, the `image` crate); all three need nothing
beyond `std::fs`, `toml`, `serde_json`, and `assistant-core`, already
workspace dependencies.

- **`analysis`** (Project Analysis): real directory traversal (skips `target`/`node_modules`/`.git`/etc., a configurable file-walk ceiling -- `TCLIS SS7` "resource limits" -- rather than an unbounded one) plus real parsing of whichever manifest it finds (Cargo.toml via `toml`, package.json via `serde_json`, pyproject.toml handling both PEP 621's `[project.dependencies]` array and Poetry's `[tool.poetry.dependencies]` table, documented as a best-effort heuristic rather than asserted as exact the way the Cargo/npm paths are). Verified against this very workspace's own `cache` crate, not a synthetic fixture, as one of its tests.
- **`diagnostics`** (Debugging): real `cargo check --message-format=json` integration. The actual JSON shape was confirmed empirically first -- a scratch crate with a deliberate `mismatched types` error, checked by hand, before any parsing code was written -- and that check surfaced a real nuance: one compile error produces *two* `"level":"error"` JSON lines (the located diagnostic, plus an unlocated `"aborting due to previous error"` summary). `error_count()`/`warning_count()` only count diagnostics with a real source location as a result, rather than reporting "2 errors" for what a user would recognize as one problem -- the raw, unfiltered messages are still all present in `DiagnosticReport::diagnostics`.
- **`generation`** (Code Generation): a real, deterministic Rust template generator (`function`/`struct`/`test` scaffolding) whose output is actually compiled in its own test, not just eyeballed -- plus an honest freeform path through `assistant_core::ResponseGenerator` (the identical trait `AssistantCore::process_message` already uses for chat, reused directly rather than duplicated the way `vision::VisionBackend` was, since code generation's input/output shape is structurally identical to chat's, unlike image understanding's). With no real backend wired in, freeform generation produces `EchoResponseGenerator`'s same honest Phase 3 stub reply -- not fabricated code.
- New `ToolCategory::Development`. `run_diagnostics` is `Destructive`, not `ReadOnly` -- a deliberate, heavily-reasoned departure (see `diagnostics::run_cargo_diagnostics`'s doc comment): `cargo check` executes `build.rs` scripts and proc-macros with this process's full privileges, unsandboxed by Cargo itself, a real Rust ecosystem risk rather than a hypothetical one. Anchored at the same level TCLIS SS6 already puts "remove packages" (a comparable "runs code from a project's own declared dependencies" risk via install scripts), not underscoped just because nothing gets deleted.
- **`integration-tests/tests/security_adversarial.rs`**: the concrete proof behind that reasoning, not just a level check -- a real crate with a `build.rs` that writes a canary file the instant it runs. `run_diagnostics_permission_gate_prevents_build_rs_from_ever_executing` confirms a denied call means the canary is never created (the gate stops the build from starting, not merely reports a denial afterward); the paired `run_diagnostics_actually_runs_build_rs_when_genuinely_approved` proves the mechanism is real by showing the canary *does* get created with genuine approval, so the denied case isn't silently vacuous.
- `config::CodingAgentConfig` (`max_files_walked`, genuinely wired through as `analyze_project`'s tool-level `max_files` override, not just a decorative default), backward-compatibility-tested the same way `[vision]`/`[performance]` were.
- 512/512 tests passing (+31 over Phase 23), across 37 verified crates (+1). `cargo fmt --all -- --check` clean workspace-wide; `clippy --all-targets -D warnings` clean across all 37 verified crates; `cargo doc --no-deps` zero warnings, rechecked including `coding-agent`.

### Phase 23 -- Vision Support

Development_plan's first "Future Phase": OCR, Image Understanding,
Screenshot Analysis. Four new crates -- `screenshot`, `ocr`, `vision`,
`vision-runtime` -- following every established cross-crate convention
(`Tool` trait, `AppError::Module`, `register_all`, crate-local
`tests/permission_integration.rs`) rather than introducing new ones.

- This session's sandbox came up completely fresh -- no Rust toolchain at all, not even the documented pinned 1.75, and `iproute2` (a previously-documented dependency of `linux-services::network`'s tests) also absent. Confirms container state, including installed tooling, doesn't persist between sessions; reinstalled `rustc`/`cargo`/`rustfmt`/`clippy` 1.75 and `iproute2` before verifying anything, and the full 447/447 baseline reproduced exactly once they were back.
- **`screenshot`**: captures the full screen via `import -window root` (X11) or `grim` (Wayland), zero new dependencies -- the same "wrap one external tool" shape `linux-services::audio`/`notifications` already established. Session detection (`WAYLAND_DISPLAY` checked before `DISPLAY`) is a pure function taking explicit `Option<&str>` arguments rather than reading process env directly, specifically to keep its tests deterministic under parallel execution rather than racing on mutable env state. Its success path is **fully verified for real** -- unlike Phase 8's audio/display/notification/clipboard modules (no sound server, backlight, or notification daemon existed to succeed against in that sandbox), a real Xvfb virtual X11 server was stood up during development and genuine capture confirmed against it: real `import` invocation, real PNG written, real dimensions read back (via a hand-rolled `IHDR`-chunk parser, spec-guaranteed to work for any encoder) matching the configured virtual screen exactly. `capture_screenshot`'s permission level is `Moderate`, not `ReadOnly` like `read_file` -- a deliberate, explicitly-reasoned departure: a screenshot exposes whatever's currently on screen without the caller naming anything, unlike a caller-named file path.
- **`ocr`**: wraps the `tesseract` CLI, zero new dependencies. Fully verified for real, unconditionally (no display server needed, just an installed binary): a synthetic PNG with known text, generated inline in the test via ImageMagick's `convert -annotate`, is read back correctly by a real `tesseract` invocation. `extract_text_from_image` is `ReadOnly`, matching `read_file`'s precedent exactly (a caller-named existing file, the same risk shape).
- **`vision`**: real image analysis (dimensions, format, per-channel mean color) via the `image` crate, pinned `=0.24.9` -- unpinned `0.25` pulls in `moxcms`, which needs the `edition2024` Cargo feature, the same class of wall `workspace.dependencies`' existing `uuid` pin already documents (confirmed empirically: `=0.25.*` fails to resolve, `=0.24.9` compiles and decodes real pixel data correctly). Also defines `VisionBackend` (mirrors `assistant_core::ResponseGenerator`'s role and shape deliberately) plus `MetadataOnlyVisionDescriber`, an honest stub that incorporates real computed facts without ever claiming to have interpreted image content -- same reasoning as `EchoResponseGenerator`. `describe_image` is `ReadOnly`, same reasoning as `extract_text_from_image`.
- **`vision-runtime`**: a Candle-based CLIP zero-shot image classifier implementing `vision::VisionBackend`, in the same unverified-in-this-sandbox category as `llm-runtime` (Candle needs rustc 1.88+; confirmed the wall reproduces exactly, including the same `getrandom`/`edition2024` dependency-resolution failure `uuid`'s comment already names). Its doc comment is explicit that it falls a step short of `llm-runtime`'s own verification bar: `ClipConfig`'s real field shape was confirmed against actual fetched candle-transformers source (quoted, with commit hash, in a real GitHub issue), but constructor/method names below that were reasoned from Candle's own established `VarBuilder`+`Config` convention (confirmed elsewhere in this exact workspace, in `bert.rs`/`llm-runtime`) rather than independently re-fetched for this specific module -- said plainly rather than implying parity it doesn't have. Candidate labels are supplied by the caller (zero-shot classification, not open-ended captioning) -- an honestly-scoped Phase 23 capability, not a stand-in for a future captioning model.
- New `ToolCategory::Vision` (`tool-framework`) -- not in TCLIS SS4's original list, the same kind of later, planned addition `Search`/`Automation` already were.
- `config::VisionConfig` (`ocr_language`, `screenshot_dir`), `config/default.toml`'s new `[vision]` section, both backward-compatibility-tested the same way Phase 18's `[performance]` section was (a config file predating Phase 23 still loads with sane defaults).
- `integration-tests/tests/security_adversarial.rs`: extended, not duplicated -- `ocr`/`vision`'s tools inherit `read_file`'s existing documented unscoped-path finding exactly (same `ReadOnly` level, same reasoning, confirmed concretely rather than assumed from the level alone), and a new test confirms `screenshot`'s `Moderate` level is the genuine exception, actually denied by a confirmation handler that says no.
- `integration-tests/tests/cross_crate_flows.rs`: a real captured screenshot (via Xvfb) hand off to `ocr`'s tool through the same router in one scenario -- the first time these two new crates' output/input were proven compatible in practice, not just on paper.
- **Found and fixed a pre-existing issue, unrelated to this phase's own changes**: `example-plugin::plugin_free_string` took a raw pointer and dereferenced it (via `CString::from_raw`) without being marked `unsafe fn` itself -- valid, no-longer-latent `clippy::not_unsafe_ptr_arg_deref` finding surfaced by this session's freshly-installed clippy, not something Phase 11 missed structurally (the unsafe *operation* was already correctly scoped and commented; only the function signature itself was the gap). `plugin_manager::dynamic` already declared this symbol's expected type as `Symbol<unsafe extern "C" fn(*mut c_char)>`, so marking the export `unsafe extern "C" fn` (plus the `# Safety` doc section clippy then also required) brings the real signature in line with what its only caller already assumed -- zero calling-convention change, confirmed by rerunning `plugin-manager`'s real dynamic-loading tests against the rebuilt `.so` afterward.

See `docs/RELEASE_NOTES.md` for the full reasoning.
- `docs/RELEASE_NOTES.md`: an honest assessment against PRD SS18's Definition of Done (two of six criteria fully met, two met at the library level but not end-to-end, two not met), a complete list of known limitations, and a concrete, dependency-ordered path to an honest future v1.0.0.
- `docs/PERFORMANCE_REVIEW.md`: every measurable target from TDS SS9/DBDMS SS13/Archd SS19 checked against real, reproducible benchmark numbers (not projections) -- memory retrieval, database startup, and indexed search all clear their stated targets by 50-500x. Targets needing the assembled app (startup time, streaming, idle CPU) are marked honestly unverifiable rather than assumed. Includes an honest linear-extrapolation caveat: `vector_db`'s O(n) search would likely miss DBDMS's 50ms target somewhere before 1 million entries, not a problem at today's scale but worth naming.
- **Bug fix**: `sandbox::FilesystemSandbox::restrict_current_process()` (real, tested Landlock-restriction code since Phase 16) is now actually called at `app` startup, closing the exact gap Phase 19's security tests documented (file-reading tools had no path-scoping and nothing applied the sandbox that would provide it). Restricts the process to `config/`, `models/`, `assets/`, `data/`, `logs/`; logs the real `EnforcementStatus` (Landlock enforcement is confirmed not active in this specific development sandbox, same finding as Phase 16, expected to work on a real target desktop) rather than assuming success. Verified compiles and runs correctly via a throwaway harness (this project's established technique for `app`-adjacent code); `app` itself remains unverified for the usual reason.
- Branch `lts/0.1.0-foundation` created at this commit: a stable, fully-tested reference point for future work once a modern toolchain unblocks Slint/Candle.
- 447/447 tests passing, unchanged (this phase's only code change was the sandbox wiring, additive and covered by the harness above, not by a crate this session already had unit tests for).
